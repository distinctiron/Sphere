A language model is a function from tokens to tokens. Yet assistants search the web, query databases, edit files and book meetings. How does a text predictor *do* anything?

It doesn't. The model **asks**, and ordinary code acts. This lesson is about that exchange, usually called <Term id="tool-calling">tool use</Term> or function calling. It is the single mechanism behind every agent, coding assistant and "computer use" demo you will read about. Once you see it clearly, you can tell what a model can and cannot do with tools, and where the power, and the risk, actually sits.

## The picture

<Recall id="model-api">

A model API call is one context in, tokens out, and the response carries a stop reason saying why generation ended. With structured output, sampling is constrained so the reply parses against a schema, which lets code act on it.

</Recall>

Put those two ideas together. A reply does not have to be an answer for a person. It can be a **request for the harness**, written in a structure the harness can parse: "call `get_weather` with `city = Paris`". The API marks it with a stop reason that means "I am waiting for a tool". The harness runs the real code, writes the output into the context, and calls the model again. The model reads the result like any other text and carries on.

<KeyIdea>

A tool call is **text the model writes and the harness chooses to act on**. To the model, a tool is a description in its context and, later, a result in its context. All the capability and all the risk live in the harness code that executes the request.

</KeyIdea>

## Anatomy of a call

Five steps, the same across providers.

1. **Declare.** The request includes tool definitions. Each has a name, a description and an <Term id="tool-schema">input schema</Term>, usually JSON Schema.
2. **Decide.** The model reads the definitions with everything else and may emit a tool call instead of (or after) some text. The API returns it as a structured block with an id, the tool name and arguments, and a stop reason such as `tool_use`.
3. **Execute.** The harness validates the arguments, runs the function with its own credentials and network access, and captures the output or the error.
4. **Return.** The harness appends two things to the history: the assistant turn containing the call, and a <Term id="tool-result">tool result</Term> message carrying the output and the call's id.
5. **Continue.** The harness calls the model again with the longer context. The model answers, or calls another tool.

A definition, and the history after one round trip, look roughly like this:

```json
{ "name": "get_weather",
  "description": "Current weather for a city. Use for questions about present conditions, not forecasts. Returns temperature in °C and a short summary.",
  "input_schema": { "type": "object",
                    "properties": { "city": { "type": "string", "description": "City name, e.g. Paris" } },
                    "required": ["city"] } }
```

```json
[ { "role": "user", "content": "Is it warmer in Paris or Tokyo right now?" },
  { "role": "assistant", "content": [
      { "type": "tool_use", "id": "t1", "name": "get_weather", "input": { "city": "Paris" } },
      { "type": "tool_use", "id": "t2", "name": "get_weather", "input": { "city": "Tokyo" } } ] },
  { "role": "user", "content": [
      { "type": "tool_result", "tool_use_id": "t1", "content": "18 °C, light rain" },
      { "type": "tool_result", "tool_use_id": "t2", "content": "24 °C, sunny" } ] } ]
```

Look at what the model never touches. It never sees an API key, never opens a socket and never runs a line of code. The tool results arrive in the history under the user role here, because from the model's point of view they are simply more input. Everything the model "does" in the world happens because some harness decided to carry out a piece of text.

Why does a model emit well-formed calls to a tool it has never seen? Because post-training taught it the *general* skill: read a schema in the context, and when a tool would help, write a call in the trained format. The specific tool is just context. That is why the description is the real interface: **the documentation is the API**.

## Designing tools a model can use

Tool definitions are context, and everything from context engineering applies.

<Recall id="context-engineering">

Every token in the window costs money and prefill time and competes for attention, and a stable prefix can be reused from the prompt cache. The model copies whatever the context demonstrates, and it uses clear, specific, well-structured material best.

</Recall>

- **Descriptions are prompts.** Say what the tool does, when to use it and when not to, what it returns and the formats of its inputs. Two tools with overlapping descriptions produce a coin-flip between them.
- **Fewer, sharper tools.** Every definition is resent on every call and is one more option to weigh. A single `search_orders(customer, status, date_range)` usually beats five narrow variants.
- **Results are context too.** Return what the model needs for its next decision, not a 50 KB raw API response. Include identifiers it can pass to follow-up calls. A bloated result is paid for on every later call in the conversation, because it stays in the history.
- **Errors are results.** When a call fails, return a message the model can act on: "date must be YYYY-MM-DD; got 'next friday'". The error enters the context, and the next call can fix it. A harness that crashes or returns "error" throws away the model's chance to recover.
- **<Term id="parallel-tool-calls">Parallel calls</Term> save round trips.** When lookups are independent, models can emit several calls in one turn, as in the figure. The harness runs them concurrently and returns all results together.
- **<Term id="tool-choice">Tool choice</Term> can be forced.** APIs let you allow tools freely, require some tool, require a specific one, or forbid them. Forcing a single tool whose schema is your desired output is a common way to get structured data out of a model.

<Example title="what a round trip costs">

A support assistant has an 8,000-token context (instructions, tool definitions and the conversation so far). A question needs two independent lookups, and each tool call plus its result adds about 150 tokens to the history.

**One call at a time:** model call 1 reads 8,000 tokens and requests lookup A; call 2 reads 8,150 and requests lookup B; call 3 reads 8,300 and answers. That is **24,450 input tokens** and three sequential model latencies, plus two tool latencies.

**In parallel:** call 1 reads 8,000 and requests both lookups; call 2 reads 8,300 and answers. That is **16,300 input tokens**, a third less, and one fewer model latency. Because every model call re-reads the whole context, round trips, not tool calls, are the unit of cost.

</Example>

## Reason with it

**Why does a model sometimes call a tool with an argument it made up, such as an order id it never saw?** Arguments are sampled tokens, exactly like prose. A schema, even an enforced one, guarantees the argument is a string of the right shape, not that it refers to anything real. So the harness must validate arguments against reality. The best response is an error result that tells the model how to find a valid id, and for anything irreversible, a check before acting.

**Why can adding a tool make an assistant worse at tasks that do not use it?** The new definition is resent on every call. It is more tokens, and one more option competing for the model's decision. If its description overlaps an existing tool, the model will sometimes pick the wrong one. Tools are not free capabilities; they are context. That cost is what <Preview id="skills-mcp">loading capabilities only when needed</Preview> addresses.

**If the model only emits text, why is tool use a security question at all?** Because the harness turns that text into real actions with real credentials. Whatever can influence the model's context, including the output of an earlier tool such as a fetched web page, can influence which calls it writes. The protection has to live where the power is: in what the harness allows, checks and asks a human about. That is a thread through <Preview id="harness-engineering">harness engineering</Preview> and <Preview id="agent-security">agent security</Preview>.

## Where this picture breaks

- **Some tools run on the provider's side.** APIs now offer built-in tools such as web search or code execution that the provider runs for you. The pattern is identical; the harness executing the call simply belongs to the provider.
- **Models are not compilers.** They may skip a tool they should use, call one they do not need, or misread a result. How reliably a model uses tools is learned behaviour, and it varies between models and tasks.
- **One exchange is not an agent.** Here the model called tools once and answered. Let it keep calling tools, reading results and deciding what to do next, and you have <Preview id="agent-loop">an agent loop</Preview>, where small per-step error rates compound.
- **"Computer use" stretches the picture without breaking it.** When the tools are "take a screenshot", "click at (x, y)" and "type text", the model operates a whole computer. It is still writing requests, and a harness is still carrying them out.

## Why it matters in the feed

"Function calling", "tool use", "computer use", "browser agents" and the Model Context Protocol are all this lesson at different scales. When a lab reports better tool-use benchmark scores, it means its model more reliably chooses the right tool, fills in arguments correctly and uses results well. When a product announces an integration with some service, it has written a tool, a description plus code that the harness runs.

## Recap

- A model cannot act; it writes a structured request (a tool call) that the API returns with a tool-use stop reason, as in the model API lesson.
- The harness validates and executes the call with its own credentials, appends the result to the history, and calls the model again. A tool call is two model calls with real work in between.
- Tool definitions and results are context. Descriptions are prompts, results should be concise, and errors should teach, following context engineering.
- Round trips, not tool calls, are the unit of cost, because each model call re-reads the whole context. Parallel calls cut round trips.
- Schemas constrain shape, not truth, so validation and permission checks belong in the harness, where the power is.
